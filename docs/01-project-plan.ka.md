# Holliday Planner — პროექტის გეგმა

მომზადების თარიღი — 2026-11-10.

სტატუსი — საწყისი სამუშაო ვერსია. მოცემული ფარგლები და შეფასების წონები განხორციელების წინადადებებია.

## 1. პროექტის არსი

Holliday Planner ეხმარება ადამიანს ან მეგობრების ჯგუფს დასვენების დაგეგმვაში. გადაწყვეტილება ეფუძნება ინტერესებს, ბიუჯეტს, მგზავრობის პირობებს, ამინდის ხელმისაწვდომ მონაცემებსა და სეზონის შესაბამისობას.

მომხმარებლის მთავარი ამოცანაა რამდენიმე ეკრანზე მიიღოს დასაბუთებული გეგმა, შეადაროს ალტერნატივები და მოიწვიოს თანამგზავრები.

საწყისი სამიზნე აუდიტორიაა საქართველოში მოკლე დასვენების დამგეგმავი ადამიანი. საწყისი ინტერფეისის ენაა ქართული, ვალუტა — GEL. გაფართოება მოიცავს სხვა ენებს, ქვეყნებსა და შეტყობინების არხებს.

## 2. ძირითადი სცენარი

1. მომხმარებელი რეგისტრირდება ელფოსტითა და პაროლით და ადასტურებს მისამართს.
2. ავსებს ინტერესებს, დასვენების სტილს, ჩვეულებრივ ბიუჯეტსა და მგზავრობის არჩევანს. ინტერესების შეცვლა მოგვიანებითაც შეუძლია.
3. პირად სივრცეში ხედავს მომავალ გეგმებს, მონახაზებსა და წარსულ მოგზაურობებს.
4. ქმნის გეგმას ფორმით ან ბუნებრივი ენით. AI-ის მიერ ტექსტიდან ამოკითხული ველები ჩანს შესასწორებელ ფორმაში.
5. უთითებს ქალაქს, ზუსტ წელსა და თარიღებს, გამგზავრების ადგილს, ადამიანების რაოდენობას, ტრანსპორტსა და ბიუჯეტს.
6. სურვილისამებრ ამატებს თანამგზავრების ელფოსტებს. ბიუჯეტის ერთეული აშკარად ირჩევა — ერთ ადამიანზე ან ჯგუფზე, სრული მოგზაურობისთვის.
7. აპლიკაცია იღებს ამინდისა და ადგილის მონაცემებს და ითვლის ხარჯების დიაპაზონს.
8. AI ქართულად განმარტავს უპირატესობებს, რისკებს, მონაცემების ნაკლოვანებებს და სთავაზობს დღის გეგმასა და ალტერნატივებს.
9. მომხმარებელი ადარებს ვარიანტებს, ასწორებს პირობებს და ირჩევს საბოლოო გეგმას.
10. ადასტურებს გეგმის ვერსიასა და მიმღებებს. სისტემა იწყებს მოწვევების გაგზავნას.
11. სტუმარი მოწვევის ბმულით პასუხობს. ორგანიზატორი ხედავს მონაწილეთა პასუხებსა და გაგზავნის მდგომარეობას.
12. მოგზაურობის შემდეგ მომხმარებელი აღნიშნავს განხორციელებას, რეალურ ხარჯსა და საკუთარ შეფასებას. წარსული თარიღი თავისთავად განხორციელებას არ ადასტურებს.

### მაგალითი

„2026 წლის 15–16 დეკემბერს მინდა ბაკურიანში წასვლა 3 მეგობართან ერთად. თბილისიდან მანქანით მივდივართ. სრული ბიუჯეტი თითო ადამიანზე 300 ლარია. გვინდა თოვლი, სეირნობა და მშვიდი გარემო.“

სისტემა უნდა გადაამოწმოს ადამიანების რაოდენობა, ღამეების რაოდენობა და ბიუჯეტის მნიშვნელობა. დარჩენილი გაურკვეველი ველები მომხმარებელს ეკრანზე ეჩვენება.

## 3. პირველი ვერსიის ფარგლები

### ანგარიშები და ისტორია

- რეგისტრაცია, ავტორიზაცია, გასვლა და პაროლის აღდგენა.
- ინტერესების შევსება და რედაქტირება.
- პირადი გეგმების შექმნა, შენახვა, რედაქტირება და წაშლა.
- მონახაზი, დაგეგმილი, გაუქმებული და დასრულებული მოგზაურობების განყოფილებები.

### დაგეგმვა და შეფასება

- საწყისი მიმართულებების მცირე კატალოგი საქართველოში, მათ შორის ბაკურიანი.
- თარიღები, გამგზავრების ადგილი, ტრანსპორტი, ჯგუფის ზომა, ინტერესები და ბიუჯეტი.
- ამინდის API და წყაროს/მიღების დროის ჩვენება.
- სეზონურობის მოკლე ცნობარი წყაროსა და განახლების თარიღით.
- საცხოვრებლის, ტრანსპორტის, კვებისა და აქტივობების ხარჯების დიაპაზონი.
- AI შეფასება, დასაბუთება, მოსამზადებელი ნივთები და 2–3 ალტერნატივა.
- შეცვლილი ადგილის ან თარიღის ალტერნატივის დამოუკიდებელი გადამოწმება.

### ჯგუფური დაგეგმვა

- მოწვევის მიმღებების წინასწარი გადახედვა და მომხმარებლის დადასტურება.
- ინდივიდუალური წერილები და პასუხის ვადიანი ბმული.
- პასუხები „მოვდივარ“, „ვერ მოვდივარ“ და „ჯერ არ ვიცი“.
- წერილის გაგზავნისა და სტუმრის პასუხის ცალკეული მდგომარეობები.

### შემდეგი ვერსიების კანდიდატები

- ჯგუფის საერთო თავისუფალი თარიღების შერჩევა.

## 5. მონაცემების სიზუსტის წესები

### ამინდი

სისტემა არჩევს მოგზაურობის ადგილის დროის სარტყელს. თარიღები ინახება აშკარა წლით. პროგნოზი გამოიყენება მხოლოდ პროვაიდერის ხელმისაწვდომ ინტერვალში და თითოეული მოგზაურობის დღისთვის მოწმდება დაფარვა.

შორეული თარიღებისთვის გამოიყენება შესაბამისი ისტორიული პერიოდის სეზონური სურათი, შესაბამისი წლებისა და წყაროს მითითებით. ეკრანზე ცალკე ჩანს მონაცემის ტიპი და სანდოობის შეზღუდვა. ახლო და შორეული დღეების შერეულ ინტერვალში დღეები ცალ-ცალკე ინიშნება.

სეზონის ცნობარი აღწერს ტიპურ პირობებს. გზის გახსნა, საბაგიროს მუშაობა ან სასტუმროს ხელმისაწვდომობა საჭიროებს მიმდინარე ოფიციალურ წყაროს.

### ხარჯები

საწყის ვერსიაში ხარჯები შეიძლება ეფუძნებოდეს ხელით შედგენილ, წყაროებით გამყარებულ ფასების ცნობარს. თითოეული ჩანაწერი შეიცავს ადგილს, კატეგორიას, ერთეულს, ვალუტას, წყაროსა და შემოწმების თარიღს.

ხარჯის ბარათზე ჩანს სავარაუდო დიაპაზონი და მისი საფუძველი. მიუწვდომელი კატეგორია აღინიშნება უცნობად. ცოცხალი შეთავაზების დამატებას დასჭირდება შესაბამისი მიმწოდებლის API და გამოყენების პირობები.

### AI

AI იღებს სერვერის მიერ შეგროვებულ მონაცემებს და განმარტავს შედეგს. პასუხი შეიცავს არგუმენტებს, წყაროების მითითებებსა და გაურკვევლობებს. წყაროებს პასუხში სერვერი აკავშირებს რეალურად მიღებულ მონაცემებთან.

არასრული მონაცემების, პროვაიდერის შეცდომის ან ლიმიტის ამოწურვისას გეგმა რჩება შენახული და მომხმარებელი იღებს გამეორების შესაძლებლობას.

## 6. შეფასების წინადადება

საწყისი განხილვისთვის განისაზღვრება ოთხი კომპონენტი. წონები საჭიროებს შემდგომ პრაქტიკულ გადამოწმებას.

| --- | --- |

| ბიუჯეტთან შესაბამისობა | 30% |
| ამინდისა და სეზონის შესაბამისობა | 25% |
| მგზავრობის მოხერხებულობა | 10% |

ეკრანზე ჩანს ქულასთან ერთად გამოთვლის საფუძველი და მონაცემების დაფარვა. მნიშვნელოვანი უცნობი მონაცემი იწვევს „შეფასება არასრულია“ მდგომარეობას. სავალდებულო პირობის დარღვევა, მაგალითად ბიუჯეტის მაქსიმუმის გადაჭარბება, ცალკე უნდა გამოჩნდეს საერთო ქულის მიუხედავად.

მოგზაურობის იდეის მოწონება და მოწვევების გაგზავნა მომხმარებლის ცალკეული მოქმედებებია. რეკომენდაციის ქულა ვერ ადასტურებს მოგზაურობის უსაფრთხოებას.

## 8. სამუშაო გეგმის შესრულების ინსტრუქცია

1. აირჩიე მიმდინარე საგნის ერთი მოთხოვნა მოთხოვნების ცხრილიდან.
2. შეამოწმე მასზე დამოკიდებული სამუშაოების მდგომარეობა.
3. შექმენი მცირე ფუნქციური ცვლილება და საჭიროების მიხედვით გამოიყენე ცალკე Git ტოტი.
4. გაუშვი ცვლილებისთვის შესაბამისი შემოწმება და გადაამოწმე მომხმარებლის ჩვეულებრივი სცენარი.
5. გადაიღე კოდის და შედეგის სქრინშოთები სატესტო მონაცემებით. გამოიყენე მოთხოვნის ნომერი და ცვლილების აღწერა სახელში.
6. მოთხოვნების ცხრილში მიუთითე ფაილი, commit და მტკიცებულება.
7. შექმენი შინაარსიანი commit და ატვირთე დამოუკიდებელ GitHub რეპოზიტორიაში.
8. გადადი შემდეგ მოთხოვნაზე, როდესაც მიმდინარე პუნქტის შემოწმება დასრულდება.

## 9. მიღების კრიტერიუმები

- მომხმარებელი რეგისტრირდება, ავსებს ინტერესებს და ხელახლა შესვლისას ხედავს საკუთარ გეგმებს.
- ბაკურიანის მაგალითი ფორმიდან გადის შენახვამდე, შეფასებამდე და ალტერნატივების შედარებამდე.
- შორეული თარიღის სეზონური შეფასება, მიმდინარე პროგნოზი და ხარჯის მიახლოებითი დიაპაზონი ეკრანზე გასარჩევია.
- ფორმები ამოწმებს თარიღებს, ჯგუფის რაოდენობას, ბიუჯეტსა და ელფოსტას.
- მიმღებები და გეგმის ვერსია დადასტურებულია გაგზავნამდე.
- ხელახალი დაწკაპუნება ან ქსელის დროებითი შეცდომა იწვევს თანმიმდევრულ მდგომარეობას და დაცულია იმავე მოწვევის უნებლიე დუბლირება.
- რეალურად მიღებული API მონაცემები და სატესტო მასალა მონიშნულია შესაბამისი წარმომავლობით.
- დასრულებულია საგამოცდო მოთხოვნების ცხრილი, GitHub-ის ისტორია, ანგარიში და პრეზენტაცია.
